# Соглашения репозитория

`py-checks` — движок архитектурных правил. Библиотека везёт правила, проект
везёт свою архитектуру: ни одного имени чужого проекта внутри `src` быть не
должно. Правило без таблицы проекта молчит.

## Раскладка

| Пакет | Что внутри |
|---|---|
| `config` | чтение настроек: свой файл или `[tool.py-checks]`; никого не знает |
| `core` | реестр, прогон, разбор файла, нарушение, маркеры, автофикс, вывод |
| `checks` | правила, по пакету на группу, по модулю на правило |
| `contracts` | сборка `.importlinter` из таблицы слоёв |
| `sync` | файлы, которые библиотека собирает проекту |
| `cli` | команды; видит всех |

Слои описаны в `py-checks.toml` и проверяются import-linter. Вверх не смотрят:
`checks` не знает `cli`, `core` не знает `checks`.

## Команды

```bash
uv run pytest -q                 # тесты
uv run ruff check . && uv run ruff format .
uv run pyright                   # strict
uv run py-checks run             # библиотека проверяет сама себя
uv run pre-commit run --all-files   # всё сразу, ~7 секунд
```

Хуки бегут на коммит, отдельной стадии pre-push нет.

## CI

`ci.yml` — на pull request и на пуш в `main`/`develop`: тот же набор, что в
хуках, плюс `py-checks run --all` (правила, которым нужна живая среда — в хуке
им не место) и `cz check` по диапазону коммитов: хук `commit-msg` локальный, а
сюда сообщения приезжают уже написанными.

`release.yml` — на тег `v*`: собрать, опубликовать на PyPI доверенной
публикацией, создать релиз на GitHub. Версию поднимает `cz bump` на машине
автора — он же ставит тег и дописывает CHANGELOG.

Действия закреплены по SHA с комментарием-версией, права выдаются по задаче, а
не всему файлу, у задачи с токеном PyPI исходников нет вовсе. Сами процессы
сторожат `actionlint` и `zizmor` — они же хуки.

## Как добавить правило

1. Модуль `src/py_checks/checks/<группа>/_<имя>.py`: класс правила и модель его
   настроек.
2. Выставить оба наружу из `__init__.py` группы, в `__all__`.
3. Объявить в `pyproject.toml`, в группе `py_checks.checks`; список
   отсортирован. Забытый шаг ловит `tests/test_registry.py`.
4. Фикстуры `tests/checks/<код>/` с `pyproject.toml`, `ok/` и `bad/` внутри;
   снимок — `uv run pytest --snapshot-update`. Правилу про проект —
   `tests/projects/<код>__<вариант>/`, вариант `__ok` обязан молчать.
5. Раздел в `docs/service.md`: таблица для типового сервиса и объяснение, зачем
   правило существует. Строку в `docs/current.md` — он не в git.

Отдельный коммит на правило.

## Как писать правило

- Класс с `code`, `Settings`, `scope`, `marker` и `run`. Никакого наследования:
  ядро видит правило протоколом.
- `run` возвращает нарушения и ничего не печатает. Узел превращается в
  нарушение через `Violation.from_node` — колонку сдвигает он.
- Настройки — модель pydantic поверх `CheckSettings`; правило, зависящее от
  места, берёт `ZonedSettings` и сужается через `zoned()`.
- Помощники правила живут внутри его класса: лист — `@staticmethod`, зовущий
  другого — `@classmethod`. Слово языка правилу не принадлежит: «как зовут
  узел» — `checks/_names.py`, «где лежит файл» — `checks/_location.py`, «что тут
  объявлено» — `checks/_kind.py`.
- Докстринг класса — то, что печатает `explain`: чем плохо нарушение, а не как
  устроен код. Кончается строкой `Настройки: ...`.
- Сообщение говорит, что не так и чем это заменить. Русский, без кодов вида
  «правило №14».
- Аргументы только именованные, `from __future__ import annotations`,
  `TYPE_CHECKING` для типов, `Final` и `ClassVar` для констант.

## Замер перед тем, как считать правило готовым

Правило гоняется по четырём справочным сервисам (`personal_bot`, `beauty`,
`betting`, `trading`) с их собственными таблицами. Два числа обязательны:

- сколько нарушений — ноль означает, что соглашение и правда соблюдается;
- **зубы**: прогон, доказывающий, что правило видит код, — с пустым списком
  исключений или с намеренно сломанным примером. Ноль без зубов ничего не
  значит: так же выглядит правило, которое ничего не проверяет.

Всё, что меняет поведение, сверяется выводом до и после: строка в строку.

## Настройки

Либо `py-checks.toml`/`pychecks.toml` (с точкой в начале или без), либо секция
`[tool.py-checks]`. Два места разом — ошибка, а не слияние. Таблиц проекта
внутри библиотеки нет и не будет.

## Пометки

`# check-ok: <код>: <причина>` снимает одно правило; слово группы
(`# db-ok`, `# type-ok`, …) — любое из группы. Пометка без причины или с
опечаткой в коде сама становится нарушением; ядро следит за этим, правила про
пометки не знают.

## Коммиты

Conventional commits, русский текст, `cz check` проверяет форму. Тема — 72
символа, тело — 100.

**Никаких трейлеров об авторстве инструмента: ни `Co-Authored-By`, ни строки
«Generated with», ни подписи эмодзи. История принадлежит автору.**
